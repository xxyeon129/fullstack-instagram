# Architecture Decision Records

## 철학
이 프로젝트는 **작동하는 최소 구현(MVP)과 가독성**을 최우선으로 한다.  
현재 우선순위인 인증/게시물 기능을 안정적으로 제공하기 위해, 복잡한 분산 구조보다 **도메인 중심 레이어드 단일 모듈**을 유지한다.  
공통 규약(`ApiResponse`, `ErrorCode`, `CustomException`)으로 일관성을 확보하고, 인프라 의존성은 추상화(`ImageStorage`)를 통해 단계적으로 확장한다.

---

### ADR-001: 도메인 중심 레이어드 단일 모듈(`backend`) 유지
**결정**: `backend` 단일 모듈에서 `controller -> service -> repository` 레이어를 유지하고, 패키지는 `user`, `post`, `global` 등 도메인 중심으로 분리한다.
**이유**: 현재 구현 범위(P0: 인증/게시물)에서 개발 속도와 변경 용이성을 확보하기에 가장 효율적이다. 팀이 빠르게 기능을 추가하고 테스트하기 좋고, 과도한 모듈 분리로 인한 운영/빌드 복잡도를 줄일 수 있다.
**트레이드오프**: 기능이 늘어날수록 모듈 경계가 약해질 수 있고, 대규모 확장 시 멀티 모듈/마이크로서비스 대비 독립 배포 유연성이 낮다.

### ADR-002: JWT 기반 Stateless 인증 + Redis Refresh Token 저장
**결정**: Access Token은 JWT로 검증하는 Stateless 방식으로 처리하고, Refresh Token은 Redis에 저장/검증한다.
**이유**: API 서버 확장 시 세션 공유 부담을 줄이면서 인증 성능을 확보할 수 있다. 또한 Refresh Token을 서버 측(Redis)에서 통제해 재발급/폐기 시나리오를 안전하게 처리할 수 있다.
**트레이드오프**: 순수 Stateless보다 운영 복잡도(Redis 의존성)가 증가하며, 토큰 관리 정책(만료/재로그인/동시 로그인) 설계를 명확히 유지해야 한다.

### ADR-003: 이미지 저장은 `ImageStorage` 추상화 + Local 기본 구현
**결정**: 서비스 로직은 `ImageStorage` 인터페이스에 의존하고, 현재 기본 구현은 Local 저장소를 사용한다. S3는 확장 가능한 구현체로 준비한다.
**이유**: 초기 개발/테스트 환경에서 외부 인프라 의존성을 최소화하면서도, 운영 단계에서 S3로 전환 가능한 구조를 확보할 수 있다.
**트레이드오프**: Local 저장소는 다중 인스턴스 환경과 내구성 측면에서 한계가 있으며, 운영 전환 시 스토리지 마이그레이션/URL 정책 정합성 작업이 필요하다.
